# 調査

## 目的

調査の目的は、依頼された問いに根拠付きで答え切ることである。答えるべき問いを減らして手間を抑えてはならない

## 1. 問いを確定する

- 依頼を「何に答えるか」の一文に書き直す
- 依頼の元に別の質問者がいる場合（Slack スレッドの質問、チケットのコメントなど）は、その質問者の問いも答える対象に含める
- 論点の選択が必要な場合、まず依頼と資料から決める。資料から決まらない場合だけユーザーに確認する

## 2. 結論に必要な問いへ分ける

- 作業する前に、結論を出すために答えが必要な問いを並べる。どれか一つでも答えが欠けると結論が出ない、という関係にある問いを並べる
- 調査の途中で新たに必要と分かった問いは追加する
- 時間や負荷を抑えるときは、調べ方を軽くする。問いを省いて軽くしない

## 3. 確かめられることを仮定しない

- 調べれば分かる値・事実・既存の運用を、仮定で埋めて説明しない
- 断定は確かめた範囲に限る。資料や検索結果の一部から、実例・必要性・不可能性を一般化しない
- 対策や案を提案するときは、その前提（原因、制約、既存の手段）を先に確かめる

## 4. 空振りしたら前提を確かめ直す

- ツールの結果が空・エラー・想定外のときは、取得できないと結論する前に前提を確かめ直す。例: パス、worktree、ブランチ、引数、権限の範囲、別のクライアントや API（`gh`、CLI、MCP の別ツール）、別の資料
- ブロッカーとしてよいのは、次のいずれかに当たる場合だけである
  - 必要な権限・認証・アクセス手段が無い
  - 必要な情報が存在しない
  - ユーザーの判断や操作が必要
- ブロッカーとして報告する場合は、試した手段を二つ以上示す

## 5. 報告前に完了を判定する

- 2で並べた問いの一つ一つについて、根拠付きで答えたか、4のブロッカーに当たるかを確かめる
- どちらでもない問いが残っている場合は報告せず、調査を続ける
- 「確認していない」「見ていない」「読んでいない」などの記載で、答えやブロッカーの代わりにしない

## 6. 報告する

問いの数にかかわらず、次の形式で報告する。この形式は5の判定結果をそのまま示すためのものである

```
## 結論
問い: <この調査で答える問いを一文で>
答え: <答え>（1〜3行）

## 問いごとの答え
| 問い | 答え | 根拠 |
|---|---|---|
| <結論に必要な問い> | <答え> | <URL・パス・チケットID・コマンド> |

## 見立て・提案
- <事実から言えること、または提案>（どの根拠から言えるかを添える）

## ブロッカー（ある場合だけ）
- <問い>: 試したこと <手段A、手段B> → 障害 <権限が無い・存在しない・ユーザーの判断が要る> → 解消に必要な条件 <何があれば答えられるか>
```

- 根拠の欄には、確かめた出典を書く。根拠を書けない問いは、答えの欄ではなくブロッカーに書く
- 確かめた事実と、見立て・提案を混ぜない
