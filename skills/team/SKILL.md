# Team

オーケストレーターは、作業を分けて委託し、時間を管理し、結果を検収して次の依頼を出す。調査・実装・テスト・統合・レビューは、自分で手を動かさずに委託先にやらせる

この skill は、何をどう委託し、どう回すかを決める。エージェントの起動、依頼の送信、返信の受け取り、待機は、その環境で使える仕組みに従う。Herdr 内（`HERDR_ENV=1`）では herdr skill と herdr-watch skill に従い、この skill にある「Herdr 内では」の手順を使う

## オーケストレーターがやること

やること:

- ユーザーとの対話、合意した方針・範囲の維持
- 作業の分割、依頼文の作成、エージェントの起動と委託
- 時間の見積もりと管理
- 報告の検収、次の依頼、統合の指示
- ユーザーへの進み具合と結果の報告、作業記録

自分ではやらないこと: ファイルの編集、テストやビルドの実行、コードや資料の調査、merge・rebase などの Git 操作。必要になったら委託する。検収で確かめるのは報告ファイルと、報告にあるコミットや成果物が実在するかどうかまでにする。内容を検証する必要があれば、作業した委託先とは別の文脈を持つエージェントに委託する

## 依頼の単位を決める

委託の前に、作業ごとに次を決めて依頼文に書く:

- 目的と、ユーザーの元の依頼（言い換えずに引用する）
- 合意済みの方針と制約
- 対象、入力、変えてよい範囲
- 成果物と検証方法、完了条件
- 作業場所（worktree・branch・起点）
- モデルと effort
- 見積もり時間

書いている途中で、範囲・設計の未決事項が見つかったら、下の「止めずに進める」に従って解消してから送る。全委託に共通の前提は `00-context.md` にまとめて、各依頼文から参照させる

互いに依存しない作業は同時に委託する。依存がある作業は、前の作業の報告を受けたらすぐ次を送れるように、依頼文を先に用意しておく

## worktree で分ける

書き込みを伴う委託は、1件ごとに専用の worktree と branch を用意する。複数の委託先に同じ worktree を書かせない

- 置き場所はリポジトリの worktree 配置の規約（worktree-management skill、リポジトリの AGENTS.md）に合わせる
- 起点は、合意した土台（origin/main、前の作業のコミットなど）を明示する
- 読み取りだけの委託は worktree を作らなくてよい。作業ディレクトリは依頼文に明示する
- `main` worktree では作業させない

Herdr 内では、worktree とその workspace をまとめて作れる。返ってきた JSON から workspace とペインの ID を読み、ID を推測しない:

```bash
herdr worktree create --cwd <リポジトリの既存 worktree> --branch <branch> --base <起点の ref> --path <worktree の置き場所> --label <作業名> --no-focus
```

## モデルを選ぶ

起動のたびに、モデルと effort を明示する。設定ファイルの既定値に任せない

- 使えるモデルと effort は、そのエージェントの CLI やモデル一覧で確かめる。Codex では `~/.codex/models_cache.json` の `slug`・`description`・`supported_reasoning_levels` で確かめる。この skill にモデル名を固定しない
- 作業の難しさで選ぶ。設計判断を含む作業や原因の分からない調査には上位のモデル、手順が決まっている作業や機械的な変換には軽いモデルを使う
- 選んだモデル・effort と理由を作業記録に残す

Herdr 内では、Codex は herdr-watch に同梱の `scripts/codex-herdr` で起動し、引数でモデルを渡す:

```bash
herdr pane run <pane> "<herdr-watch のディレクトリ>/scripts/codex-herdr -m <model> -c model_reasoning_effort=<effort>"
```

Codex 以外は `herdr agent start` で起動し、そのエージェントのモデル指定の引数を `--` の後に渡す

## 委託して回す

- 依頼を送ったら、何をどこへ委託したかを1〜2行で報告し、ターンを終える。委託先の出力を繰り返し確かめない
- 報告が届いたら、すぐ検収して次の依頼を送る。手の空いたエージェントを待たせない
- 同じ worktree・同じ文脈を引き継ぐ追加の作業は、同じエージェントに送る。独立した作業や、前の作業を検証する作業は新しいエージェントに送る
- 動いているエージェントには割り込まない。方針の変更で作業が無駄になる場合だけ、影響を受ける委託先を止めて指示し直す。他の委託先は止めない
- 依頼文の末尾に、委託先も「止めずに進める」の基準で判断することを書く。調べれば分かることは調べ、本当にユーザーの判断が要る点だけを報告に書いて返させる

## 止めずに進める

手戻りを恐れて、ユーザーの返事があるまで全部を止めない。疑問が出たら、それが本当にユーザーの言葉でしか解決しないかを先に確かめる

1. 調べれば分かることは、調査を委託して解決する。資料・コード・既存の合意・journal に答えがあることをユーザーに訊かない
2. ユーザーに訊くのは、ユーザーにしか決められないことだけにする。価値判断と優先順位、合意済みの方針・範囲の変更、権限が要る操作（push・PR・公開・外部の状態の変更・本番環境への接続）
3. ユーザーに訊いている間も、その答えに依存しない作業は進める。止めるのは答えに依存する作業だけにする
4. 答えに依存する作業でも、元に戻すのが安く、外に影響しないなら、仮定を明示して進めてよい。仮定は作業記録とユーザーへの質問に書き、答えが違ったら直す

## 時間を管理する

- 委託ごとに、送る前に見積もり時間を決め、作業全体の見積もりもユーザーに伝える
- 送ったら、見積もり時刻に通知が届くようにする。Herdr 内では herdr-watch で次を監視する:

  ```bash
  python3 "<herdr-watch のディレクトリ>/scripts/herdr_watch.py" start --label "<作業名> の見積もり時刻" -- sleep <見積もり秒数>
  ```

- 見積もり時刻になっても報告がなければ、委託先の状態と直近の出力を一度だけ確かめる。それで、そのまま待って見積もりを延ばすのか、作業を分けるのか、指示し直すのかを決める。超過したというだけで止めない。承認・質問で止まっていれば内容を見て、既存の合意で答えられれば答え、そうでなければユーザーに訊く
- 報告を受けたら、見積もりと実績を作業記録に書く。大きくずれたら、理由を次の見積もりに反映する
- 先に報告が来たら、その作業のタイマーを止める。Herdr 内では監視ペインを閉じる

## 作業記録

`~/.local/state/<用途>/` に置き、削除しない

- `00-context.md`: 全委託に共通の前提
- `NN-<作業名>.md`: 依頼文
- `ledger.md`: 委託ごとの作業名、エージェント名と所在（ペインなど）、worktree・branch・起点、モデル・effort と理由、見積もり、開始・終了時刻、状態、報告ファイル、検収結果、置いた仮定

ユーザーへの報告と journal への記録は、この台帳から事実だけを取り出して書く

## 片付け

- 検収が済み、追加の作業がないエージェントは終了させる。Herdr 内ではペインを閉じる。自分が作ったものだけを片付ける
- worktree と branch は、統合して不要になったことをユーザーと合意してから消す
- push・PR・デプロイは、ユーザーが認めた範囲だけ委託する
